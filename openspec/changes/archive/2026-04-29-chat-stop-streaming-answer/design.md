## Context

当前流式问答由前端 `fetch + ReadableStream` 手动消费 `GET /api/ask/stream`，而不是使用原生 `EventSource`。前端只有“发送”入口，没有“停止”控制；一旦用户中断连接，当前实现会统一落入错误分支，页面展示“请求失败”，无法表达“用户主动停止”。

后端 `ErpAssistantService.streamWithRecording()` 通过 `doFinally` 在流结束时统一保存助手消息并执行计费扣除。由于 `doFinally` 同时覆盖完成、异常和取消三种信号，如果不区分终止原因，新增“停止回答”后会把取消态误处理为正常完成或通用失败。

本变更跨越前端聊天页面、流式问答编排、历史消息持久化和计费边界，适合先形成设计文档再实施。

## Goals / Non-Goals

**Goals:**
- 在流式回答进行中为用户提供显式“停止回答”入口。
- 前端将“用户取消”与“请求失败”分开处理，保留已生成内容，不展示误导性的失败提示。
- 后端将流取消识别为独立终态，保存部分回答并写入取消状态。
- 取消场景下避免重复或无依据扣费，保持历史记录与统计语义一致。

**Non-Goals:**
- 不新增独立的“取消任务”后端接口。
- 不改变现有 `/api/ask` 非流式问答行为。
- 不修改模型路由、Tool Calling、RAG 检索或系统提示词逻辑。
- 不引入新的数据库表；优先复用现有 `a_chat_message.status` 字段。

## Decisions

### 1. 前端使用 `AbortController` 中止当前流式请求

前端已经通过 `fetch()` 建立流式连接，因此最小改动方案是在 `sendQuestion()` 内为当前请求创建 `AbortController`，在“停止回答”按钮点击时调用 `abort()`。

选择原因：
- 与现有 `fetch + ReadableStream` 实现完全兼容，无需改成 `EventSource`。
- 浏览器断开 HTTP 连接后，服务端可自然接收到取消信号。
- 不需要额外的会话级取消协议，也不需要维护服务器端请求注册表。

备选方案：
- 新增 `/api/ask/stream/cancel` 接口：实现更重，需要请求标识注册和跨线程取消，不适合作为第一版。
- 改成 `EventSource`：原生 API 不支持自定义 header，而本项目依赖 `X-Ent-Code` / `X-User-Id`，适配成本更高。

### 2. 前端状态机区分完成、取消、失败三种结束态

前端将新增“当前流请求控制器”和“是否用户主动取消”的状态变量。`catch` 分支中识别 `AbortError`，取消时不插入“请求失败”消息，而是在已有助手气泡末尾追加“已终止”提示，并恢复输入框与发送按钮状态。

选择原因：
- 让 UI 语义与用户行为一致，避免主动停止后出现错误提示。
- 保留流式过程中已渲染的 Markdown 内容，符合主流 AI 产品预期。

备选方案：
- 取消后直接移除助手气泡：会丢失用户已经看到的部分回答，不利于复查。

### 3. 后端基于 Reactor `SignalType.CANCEL` 识别取消态

`ErpAssistantService.streamWithRecording()` 在 `doFinally` 中读取终止信号。正常完成按现有成功路径处理；取消时走单独分支，将已累积文本作为部分回答保存，并标记消息状态为 `cancelled`。

选择原因：
- 不需要额外传参或新增控制器接口，直接利用 Reactor 的取消语义。
- 能与当前 `contextWrite`、`TenantContextAccessor`、消息累计与 token 捕获逻辑保持同一条链路。

备选方案：
- 在 `Flux<String>` 中插入显式结束标记：仍无法替代底层网络断开产生的取消信号，而且会污染现有 SSE 文本流格式。

### 4. 复用 `a_chat_message.status` 表达取消态，不新增表结构

现有消息表和 `ChatHistoryService.saveMessage(...)` 已支持 `status` 字段，并已有 `success` / `error` 语义。实现中新增 `cancelled` 状态即可，无需改表；必要时扩展 `ChatHistoryService` 的助手消息保存方法，允许显式传入状态。

选择原因：
- 现有表结构已满足需求，避免不必要的数据迁移。
- 历史页面后续可直接根据状态展示“已终止”标签。

备选方案：
- 单独增加 `cancelled_at` 字段：对当前需求价值有限，增加迁移和兼容复杂度。

### 5. 取消场景下仅对“已观察到的实际 usage”做一次性结算

取消发生时，如果流中尚未收到可用 `Usage` 元数据，则按 0 token 记录，不执行扣费；如果取消前已观察到完整 usage，则按该 usage 结算一次。无论何种情况，取消分支不得重复调用扣费逻辑。

选择原因：
- 当前 Spring AI 流式返回中 usage 往往只在末尾或后段 chunk 中出现，取消时未必拿得到完整 token 数。
- 以“已观察到的 usage 为准”比强行估算更稳妥，避免脏账。

备选方案：
- 按部分文本长度估算 token：误差大，不适合计费。
- 取消时固定不计费：用户体验友好，但可能与已产生的上游成本不一致。

## Risks / Trade-offs

- [取消发生在 usage 返回前，token 可能为 0] → 通过“仅按已观察到 usage 结算”避免估算误差，并在日志中记录取消态以便后续评估。
- [前端按钮状态与网络状态不同步] → 将发送/停止按钮切换统一收敛到 `sendQuestion()` 的 `try/catch/finally` 和显式停止方法中。
- [部分回答入库后，历史页面无法直观看出被截断] → 持久化 `cancelled` 状态，并在历史消息展示层增加状态标识。
- [浏览器断流后上游模型可能短时间内继续生成] → 第一版接受该窗口期，只保证本服务正确取消本地流和状态；若后续需要，可再评估服务端注册表 + cancel endpoint。

## Migration Plan

1. 先上线前端停止按钮和后端取消态识别逻辑。
2. 保持 `/api/ask/stream` 路径和请求参数不变，避免前端调用协议破坏性变更。
3. 如需回滚，只需移除前端停止按钮和后端取消分支，现有 `status` 字段可继续兼容。

## Open Questions

- 历史记录页面是否需要为 `cancelled` 状态增加独立视觉标识，还是先仅保留数据语义。
- 若后续发现上游模型在客户端断连后仍持续计费，是否需要引入显式服务端取消能力。
