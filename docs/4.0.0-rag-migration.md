# 4.0.0 知识库与 RAG 引用迁移说明

## 升级边界

4.0.0 引入租户级知识库、稳定文档 ID、文档版本、回答引用快照和版本化 RAG 评测，并将本地嵌入模型切换为支持中文的 `paraphrase-multilingual-MiniLM-L12-v2`。旧版 PgVector 数据只有 `ent_code + source`，缺少 `knowledge_base_id`、`document_id`、`document_version`、`chunk_id`、`chunk_index` 和 `embedding_model`，因此不会自动进入新的受管检索链路，也不能作为可验证引用。即使旧模型同样输出 384 维向量，其语义空间也与新模型不同，禁止混用。

升级不猜测旧向量的文档身份。所有仍需使用的旧文档必须在新版本发布后重新导入。

## 发布前盘点

1. 按租户导出旧向量的 `ent_code`、`source`、分片数量和最近更新时间，形成待重新导入清单。
2. 保存每个来源对应的原始文件；包括已经具有受管文档身份但仍由 `all-MiniLM-L6-v2` 生成的文档。无法找到原文件的来源标记为待业务确认，不从向量文本反向拼装文件。
3. 备份 ERP MySQL 中的会话和计费数据，并确认 PgVector 数据库具备可恢复快照。
4. 在隔离环境执行普通离线测试；具备 MySQL、PgVector 和有效模型 Key 时，再执行显式真实评测并留存报告。
5. 确认部署节点为支持 AVX2 的 x86-64 CPU；当前随包模型为固定上游修订的 AVX2 INT8 ONNX 文件。

## 数据库变更

应用启动时会幂等执行以下变更：

- 新建 `a_knowledge_base`，保存租户知识库、状态和默认标记。
- 新建 `a_knowledge_document`，按稳定文档 ID 保存每个导入版本及 `processing/ready/failed/superseded/deleted` 状态，并记录成功入库使用的 `embedding_model`；已有表会幂等补充该可空字段。
- 为 `a_chat_message` 增加可空 `knowledge_base_id` 和 `rag_citations`；旧消息保留空值并按无引用兼容回放。

上线前应使用与生产一致的 MySQL 版本验证 DDL 权限。上线后检查两张新表、索引和消息表新增字段均已创建；不得手工给旧消息补造知识库或引用身份。

## 发布与重新导入顺序

1. 先停止旧版文档上传入口，避免盘点后继续产生旧格式向量。
2. 同一发布窗口同步部署后端和 `index.html`、`app.js`、`style.css`，避免旧前端发送缺少知识库状态的请求或误解新的 SSE 事件。
3. 启动 4.0.0，访问知识库列表以为每个租户懒创建“默认知识库”。
4. 文档列表中显示“需重新导入”的记录表示数据库虽保留旧 `ready` 状态，但旧向量不能用于当前模型检索。按发布前清单把原始文件重新上传到目标知识库，为全部需保留文档生成带当前 `embedding_model` 身份的新向量。兼容 `/api/load` 和 `/api/upload` 只代理默认知识库；非默认库使用知识库文档子资源接口。
5. 每个来源必须等待最新版本进入 `ready` 后再处理下一批；`failed` 版本保留错误摘要，上一 `ready` 版本仍可检索。
6. 抽查非流式、流式和历史回放：新回答的引用必须来自本轮召回，旧消息引用保持为空。
7. 重新导入完成并经过观察期后，只清理同时匹配 `ent_code + source`，且稳定身份字段缺失或 `embedding_model` 不是当前模型身份的旧向量。不得只按 `ent_code + source` 删除，否则会同时删除刚导入的新向量。若当前向量库删除接口无法可靠表达“字段不存在/模型身份不一致”，必须在备份后按单个旧来源先清理、再重新导入，不得在重新导入后使用模糊条件清理。

## 镜像标签发布

`docker-compose.yml` 继续使用 `ly753/spring-ai-rag-demo:latest`。发布 4.0.0 时，应从同一次构建生成 `4.0.0` 和 `latest` 两个标签，并分别推送：

```bash
git lfs install
git lfs pull --include="src/main/resources/models/embedding/model.onnx,src/main/resources/models/embedding/tokenizer.json"
git lfs fsck --pointers --objects
mvn -q "-Dtest=EmbeddingModelResourceTest" test

docker build \
  -t ly753/spring-ai-rag-demo:4.0.0 \
  -t ly753/spring-ai-rag-demo:latest \
  .
docker push ly753/spring-ai-rag-demo:4.0.0
docker push ly753/spring-ai-rag-demo:latest
```

前三条命令会把模型和分词器都下载到本地并检查 LFS 对象；随后执行的本地资源测试会校验两个文件的 SHA-256、模型结构和中文分词能力。Dockerfile 继续使用通用 Maven 打包流程，不在其中重复维护模型哈希。推送后核对两个标签的镜像摘要一致，确保 `latest` 与 `4.0.0` 指向同一个镜像内容；不要为 `latest` 单独重新构建。

## 发布后监控

- `a_knowledge_document` 中 `processing` 长时间未结束和 `failed` 版本的数量、来源及错误摘要。
- 日志中的导入失败补偿、旧版本向量清理失败和文档删除后向量清理失败。
- 知识库维度的实际召回分片数、空召回率、引用有效率以及问答 P50/P95 延迟。
- `rag_citations` 持久化失败、损坏或超过 32 KiB 后降级为空引用的数量。
- 显式评测报告中的跨租户/跨知识库召回、无效引用、证据一致性和 Recall@5 基线变化。
- 文档标题限定是否命中唯一 `ready` 来源，以及普通检索最终 topK 是否长期被单个超大文档占满。

## 回滚

1. 停止新的文档导入和替换操作，避免回滚期间产生重复版本。
2. 回滚后端与静态前端到同一旧版本，恢复旧协议组合。
3. 保留 `a_knowledge_base`、`a_knowledge_document` 以及 `a_chat_message` 的新增可空字段，不执行删表、删列或反向改写历史消息；旧版代码会忽略这些数据。
4. 旧版后端恢复知识检索前，先按完整稳定身份导出并备份 4.0.0 新格式向量，再将其从旧版访问的活动向量表中隔离或移除；随后恢复完整的发布前 PgVector 快照，或只恢复经确认的旧格式向量。不得让旧版后端直接读取仍在活动表中的新格式向量。
5. 再次升级到 4.0.0 时，恢复已备份的新格式向量或按原始文件重新导入，再按租户、知识库、文档和版本核对可用数据；不得删除其他租户或其他评测运行的数据。

回滚只恢复服务行为，不撤销新表和新字段。这样可以保留导入状态、失败证据和回答引用快照，避免再次升级时丢失可追溯信息。
